# Review Changes Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development. Controller reviews, commits and pushes the phase.

**Goal:** Review new findings against a chosen saved baseline and focus on Git changes without weakening scan coverage.
**Architecture:** Keep complete source scans and immutable comparison projections. A bounded local Git adapter reports branch, revision, selected base, changed/staged/unstaged/untracked paths. Git path selection filters findings after a full scan; it never changes resolution coverage. Distinguish working-tree content from the Git index explicitly. Persist scan revision context so old scans do not masquerade as current branch results.
**Tech Stack:** Rust process adapter and existing repository comparisons; React/TypeScript result views.
**Spec:** docs/superpowers/specs/2026-09-07-everyday-engineering.md

## Global Constraints
- Source findings always represent disk content. Staged-path views must explicitly say they do not inspect the index snapshot when partially staged content differs.
- No repository writes, checkout, hooks, network, shell interpolation, arbitrary Git options, or diff/textconv drivers.
- Resource/time-bound Git subprocesses and NUL-delimited path parsing. Missing Git/non-repositories still support ordinary scans. Handle detached/unborn HEAD, filenames with spaces/newlines, deleted files, renames and subdirectory targets.
- Preserve review/policy authority, coverage checks, immutable persisted baselines, source-root containment and existing scan budgets.
- No additional subagents; controller owns commits/pushes.

Acceptance: engineers can choose a prior completed baseline and review new findings, see which current working-tree findings relate to their Git changes, and identify the revision/coverage of the evidence. This phase deliberately performs full scans; it does not claim incremental scan speed or stage-snapshot verification.

Git safety note: disabling external diff/textconv alone does not disable clean filters or fsmonitor hooks during worktree/status operations. Explicitly disable fsmonitor and ensure repository-configured clean/process filters cannot execute (use object/index-only commands and own bounded raw-file comparisons, or a documented safe config strategy). Add a fixture repository with a malicious filter/fsmonitor command that would create a marker and assert inspection creates no marker. Do not read or print unrelated user Git credentials/config values.

CLI baseline boundary discovered during planning: src-tauri/src/cli/baseline.rs currently names every baseline-only fingerprint `resolved` without coverage, and cli/mod.rs loads the baseline AFTER writing current output. Add a focused CLI boundary subtask to this phase: load/validate the baseline and required gate arguments before scanning/output, so using the same baseline/output path cannot suppress new findings; label report-file-only absence `no longer observed` (or equivalent explicitly unverified absence) unless actual compatible coverage can be proved, keeping coverage-aware durable comparisons authoritative. Add regressions for same baseline/output path and a previously flagged skipped/deleted file. This is needed before the phase6 CI example relies on baseline gating. Do not turn legacy baseline shape support into silent identity defaults; reject empty/invalid fingerprints used for matching.
