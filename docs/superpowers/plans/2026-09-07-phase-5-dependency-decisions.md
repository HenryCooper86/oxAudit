# Dependency Upgrade Decisions Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development. Controller reviews, commits and pushes.

**Goal:** Share desktop/CLI dependency execution and explain which dependency update addresses related advisories.
**Architecture:** Extract dependency orchestration from Tauri commands into a transport-independent service over existing repository, provider clients, cancellation and event ports. Both adapters use it. Preserve complete package occurrences before deduplicating network queries. Build bounded declared dependency relationships from supported lockfiles, with explicit unknowns for unsupported formats. Derive upgrade groups from persisted evidence, without executing package managers or changing manifests.
**Tech Stack:** Rust service and parsers, SQLite canonical graph/projections, Clap, React.
**Spec:** docs/superpowers/specs/2026-09-07-everyday-engineering.md

## Global Constraints
- Preserve phase1 completeness guarantees, provider snapshot integrity, budgets, cancellation, and phase2 project checks.
- Existing raw package queries are deduplicated by ecosystem/name/version; every lockfile occurrence must remain visible independently for provenance.
- No package installation, repository code execution, auto-upgrades, arbitrary package manager commands, or hidden network expansion.
- Fixed version strings alone are not proof a combined upgrade clears all advisories. Use version/range semantics where supported; unknown when ambiguous, unsupported, prerelease or multi-range applicability cannot be established.
- Add defaulted fields for old projections; unknown relationship evidence stays unknown.
- Controller commits/pushes; no additional agents.

### Task 2: Explain dependency paths and upgrade groups

Files: focused deps relationship and upgrade modules/tests; models.rs; src/features/dependencies components/models/tests and DepsScan.tsx; README.

- [x] Extend persisted result with occurrence/relationship evidence without breaking old records. Native support must at least cover npm package-lock v2/v3 root and workspace declarations, nested/hoisted package resolution and links, with cycle/depth/node bounds. For other supported inventory formats, show lockfile locations and explicit relationship-unavailable status rather than invent parents. Read metadata only; do not invoke npm install/explain on untrusted repositories.
- [x] Hand-authored fixtures cover root direct dependency, transitive parent, two versions nested/hoisted, workspace links, repeated package across lockfiles, missing target, aliases and cycles. Derive root-to-vulnerable-package chains and which direct manifest dependency is the update entry point. Preserve dependency type (runtime/dev/optional/peer) when actually declared; unknown otherwise.
- [x] Group vulnerabilities by affected package occurrence and update entry point. Show number of related advisories, installed version, published fixed versions, dependency chain and affected workspace/lockfile. Explain whether the direct dependency can be updated or the parent needs an update. Do not offer an unsafe command for transitive packages as if they were direct.
- [x] For supported numeric semantic versions, distinguish patch/minor/major candidates; label this version-change classification, not a compatibility guarantee. If no candidate can be proven to clear all related advisory ranges, show per-advisory fixes and an explicit manual decision. Unsupported ecosystem/range/prerelease semantics remain unknown. Copyable package-manager commands only for precisely known direct dependencies, with no auto execution; otherwise copy a remediation checklist.
- [x] Add table/group detail navigation and recheck dependencies using existing service. Show grouped fixes alongside advisories, preserve original individual evidence, use accessible controls and existing UI styles.
- [x] Test group counts, location preservation, unresolved/transitive behavior and classification. Run Rust workspace tests, strict clippy, npm check/test/build, and standards export roundtrips. Update CLI and upgrade docs.

Primary references: https://docs.npmjs.com/cli/using-npm/workspaces/ and https://github.com/npm/cli/blob/latest/docs/lib/content/configuring-npm/package-lock-json.md. Verify exact parser semantics against installed lockfile fixtures and authoritative documentation.

Carry-forward parser boundary: phase1 deliberately rejects non-link npm records missing a version and skips explicit link records. Phase5 workspace support must account for legitimate versionless private workspace targets (packages/workspace metadata plus node_modules link target), without allowing malformed registry nodes to disappear into a complete empty result. Include an actual root/workspace/link trio, not just an isolated link entry. Validate local link targets/relationships and preserve unknowns when version/query evidence is unavailable.

Upgrade evidence finding: deps/osv.rs::parse_vulns currently flattens EVERY affected[] entry into fixed_versions/affected_range, without matching that entry's package ecosystem/name to the queried package, and collapses repeated event intervals to the final introduced/fixed pair. Do not use these lossy display strings to prove a combined upgrade. Add defaulted structured matching-package affected range evidence from raw OSV records, preserve all event intervals and range types, and classify historical flattened-only projections as unknown. A multi-package advisory fixture must not show another package's fix as this package's upgrade. Also test multiple disjoint intervals and introduced/fixed/last_affected/limit semantics; unsupported types remain unknown.

Primary range semantics: https://ossf.github.io/osv-schema/#evaluation (and affected ranges/events sections). Evaluate matching package identity, versions union ranges, sorted introduction/fix transitions, inclusive last_affected versus exclusive fixed/limit, and range union. A last-affected cutoff alone is not a published fixed release. Keep chosen upgrade wording limited to supplied advisory evidence.

CLI durable-history boundary: current `runs` calls FindingsService::list_recent_projects and returns source-only RecentProject rows (lastCompletedRunId), while canonical dependency runs live in the shared run store. Ensure new durable CLI dependency work is actually discoverable/exportable: add a documented compatible way to list dependency runs or run kinds and export their standards projections by returned run ID. Preserve/document existing source runs output shape; phase6 CI example will consume the final documented shape. Do not equate a source-project list with all persisted dependency history.

Grounded service extraction pointers: commands/dependencies.rs presently owns schema2 receipt helpers and the full canonical coordinator pipeline; canonical_list_runs(kind,limit) already exists at findings/repository.rs and render_stored_run in cli/mod.rs already handles dependency graph/projection exports. Extend those surfaces rather than inventing another history store. Current dedupe_dependencies deliberately keeps first ecosystem/name/version occurrence, so reserve it for provider query construction only. The service must map every inventory occurrence to provider results and canonical artifacts. Current enrichment code discards _notes/_poc_notes; preserve meaningful optional-source freshness/failure notes in defaulted result fields rather than treating unavailable enrichment booleans as known false. Keep provider completeness and optional enrichment failure semantics distinct.

Task2 parser correction from Task1 inspection: current parse_package_lock derives nested names by joining parent/node_modules/child and also walks legacy dependencies when packages exists. Correct actual queried package identity for nested/scoped installs and select authoritative packages inventory for v2/v3 (legacy dependencies is compatibility data), preserving path occurrences separately. Add regressions for both to avoid duplicate inventory/incorrect OSV queries.

Task2 UI consumer boundary: consume Task1 defaulted advisory/enrichment provenance in DepsScan result context. Show optional enrichment unavailable/stale/warnings explicitly alongside grouped decisions; historical defaulted metadata stays unknown. Do not render an unavailable KEV/EPSS/public-exploit fetch as a new known-negative assertion merely because historical boolean fields defaultfalse. Preserve the individual advisory evidence while explaining freshness.

Task1 standards preflight correction: existing VEX helper associates every advisory with every component, and existing SARIF omits dependency AdvisoryMatch. Newly exposed dependency standards must use observation→component/artifact evidence. Add two-component/one-advisory isolation fixtures and bounded SARIF advisory mapping (lockfile locations, package coordinates, no fabricated source lines) where graph supports it. If unsupported, explicitly reject that dependency format before emitting a report rather than succeeding with misleading empty findings. Keep scope to newly exercised attribution/format behavior.

Upgrade wording: display advisory-reported fixed versions and label a combined candidate as clearing the supplied supported advisory ranges. No registry/package-manager execution is authorized or needed to claim a release exists or is compatible; do not promise availability/compatibility from fixed strings. The OSV schema notes version strings may be normalized, so unsupported or ambiguous semantics stay manual.

Task2 consistency boundary: derive npm inventory coordinates, install paths, and declaration relationships from the same bounded parsed content, or verify content identity before joining separately read data. A lockfile edited between reads must not lend unrelated relationship evidence to the scanned inventory. Preserve explicit budgets and no-follow/containment behavior already in scanning; avoid additional unbounded reads.
